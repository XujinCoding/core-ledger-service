## 2. 数据库设计确认

### 2.1 BaseEntity 公共字段
所有实体类继承 `BaseEntity`，包含以下字段：

| 字段名 | 类型 | 说明 | 注解 |
|-------|------|------|------|
| `id` | Long | 主键ID | `@Id` `@GeneratedValue` |
| `memo` | String | 备注 | `@Column(length=255)` |
| `status` | Integer | 软删除标识 (1=有效, 0=删除) | `@Column(nullable=false)` |
| `createInstant` | LocalDateTime | 创建时间 | `@CreatedDate` |
| `modifyInstant` | LocalDateTime | 修改时间 | `@LastModifiedDate` |
| `version` | Integer | 乐观锁版本号 | `@Version` ✅ **新增** |

**关键决策**:
- ✅ **所有表都需要 version 字段用于乐观锁控制**
- ✅ **软删除策略**: `status=1` 有效，`status=0` 删除

---

## 3. 业务规则确认

### 3.1 账本明细修改
**问题**: 创建后是否允许修改明细（增删改商品）？

**确认**: ✅ **需要支持修改**

**实现方式**:
- 支持新增明细项
- 支持修改明细项（价格、数量）
- 支持删除明细项（软删除，`status=0`）
- 修改后自动重新计算 `total_amount`

**注意事项**:
- 使用乐观锁防止并发修改冲突
- 修改明细时需要更新账本主表的 `total_amount`

---

### 3.2 支付流水删除
**问题**: 是否允许删除支付记录？

**确认**: ✅ **可以通过 status 来软删除**

**实现方式**:
- 设置 `status=0` 实现软删除
- 删除支付记录后需要重新计算账本的 `paid_amount`
- 可能触发账本状态变更（如从 CLEARED 回到 PARTIAL）

**权限控制**:
- 建议仅管理员可删除支付记录

---

### 3.3 客户合并
**问题**: 是否需要支持客户合并功能（重复客户）？

**确认**: ❌ **不需要**

## 5. 并发控制

### 5.1 乐观锁策略
**确认**: ✅ **需要乐观锁，所有表都需要加 version 字段**

**实现方式**:
- 使用 JPA 的 `@Version` 注解
- 数据库字段: `version INT NOT NULL DEFAULT 0`
- 更新时自动递增版本号
- 版本冲突时抛出 `OptimisticLockException`

**适用场景**:
- 账本修改（防止并发修改金额）
- 明细修改（防止并发增删改）
- 支付记录（防止重复支付）
- 客户信息修改

## 6. 异常处理

### 6.1 统一错误码体系
**确认**: ✅ **需要统一的错误码体系**

**错误码设计**:

| 错误码范围 | 模块 | 示例 |
|-----------|------|------|
| 200 | 成功 | 200 |
| 400-499 | 客户端错误 | 400, 401, 403, 404 |
| 500-599 | 服务器错误 | 500 |
| 1000-1999 | 客户模块 | 1001=客户不存在, 1002=手机号已存在 |
| 2000-2999 | 账本模块 | 2001=账本不存在, 2002=状态不允许操作 |
| 3000-3999 | 商品模块 | 3001=商品不存在, 3002=分类不存在 |
| 4000-4999 | 支付模块 | 4001=支付金额超限 |
| 5000-5999 | 权限模块 | 5001=仅管理员可操作 |
| 9000-9999 | 系统错误 | 9001=乐观锁冲突, 9002=数据库错误 |

**实现方式**:
- 创建 `ErrorCode` 枚举类
- 自定义异常类携带错误码
- 全局异常处理器统一返回格式
